# Architecture

The Atlas mirrors the ecosystem of Alisson's portfolio (`alis-portfolio`, `alis-portfolio-api`, `alis-design-system`): same stack, folder layout and rules, in its own repos.

## Repos (siblings, GitHub owner `alishenriques`, all public)

| Repo | Package | Role | Deploy |
|---|---|---|---|
| `atlas-migracoes` | (private app) | Next.js App Router front-end and, later, the admin area; main repo and source of these docs | Vercel |
| `atlas-migracoes-api` | `@alishenriques/atlas-migracoes-api` | GraphQL API, database, spreadsheet importer | Vercel function |
| `atlas-migracoes-design-system` | `@alishenriques/atlas-design-system` | React components and `--atlas-*` tokens | npm, via GitHub Actions on `v*` tags |

## Labels and project board (decided by Alisson, 2026-10-18)

- **Every PR is linked to the project board** [Atlas Migrações (GitHub Project 4)](https://github.com/users/alishenriques/projects/4).
- **Every PR carries labels** for what it implements: the kind (`feature`, `fix`, `docs`, `chore`, `refactor`, `test`), the screen or module (`explorar`, `trajetorias`, `camada-historica`, `rede-relacional`, `ia-relacional`, `sobre`, `importer`, `design-system`…) and the stage (`stage-1`…`stage-4`).

## Data flow

Next.js server components → Axios POST to `NEXT_PUBLIC_GRAPHQL_URL` → GraphQL Yoga → in-memory dataset loaded per request through Drizzle → Neon Postgres. Responses are parsed with Zod on the front-end as well (`src/lib/schemas.ts`).

The spreadsheets enter the database once, from the importer CLI in the API repo (`yarn import:xlsx --dir <folder>`), run on Alisson's machine against Neon. The admin import screen planned for stage 3 reuses the same parser.

## Data model (API)

Source of truth: `atlas-migracoes-api/src/schemas/domain.ts` (Zod) and `src/db/schema.ts` (Drizzle).

- `places`: hierarchical names exactly as written in the source (historical names kept), slug id of the path, `currentName` from "[atual X]", `lat`/`lng` null until geocoded.
- `artists`: name, slug, birth/death place and date.
- `works` (id = MAC USP tombo), `exhibitions` (EH./EX./EM. ids) and `publications` (PB. ids), linked through `work_exhibitions` and `work_publications`.
- `import_batches`: one row per import with counts, unresolved references and warnings, for review.
- **`FuzzyDate`** (jsonb): `{ raw, year, endYear, iso, precision }`, precision `day | month | year | circa | range | unknown`. The UI must render a date according to its precision, never as more exact than it is.

What the data does **not** have: arrival year or route to Brazil, images. The map links each artist's documented points in date order (atlas-migracoes#11, decided by Alisson, 2026-10-20): the leg from the birthplace to the first documented place in Brazil is drawn in gold, with no intermediate route reconstructed, and the rest dashed; exhibitions in the artist's lifetime and the place of death are further points of the trajectory. Sobre says the same in "Dados". This holds until the migration event becomes editable in the admin area.

## API (`atlas-migracoes-api`)

- `src/app.ts`: `createApp(env, { db })` builds the Yoga instance; used by `src/index.ts` (local) and `api/graphql.ts` (Vercel). `vercel.json` rewrites `/graphql` and pins the "Other" preset (`framework: null`, output `public`), because Vercel would otherwise detect a Vite site from the `vite` dev dependency that vitest needs.
- `src/graphql/schema.ts`: read-only queries `meta`, `stats`, `artists(filter)`, `artist(slug)`, `places`, `exhibitions(placeId)`, `work(id)`. Throw `GraphQLError` for client-visible errors (`BAD_USER_INPUT`).
- **Demo mode:** without `DATABASE_URL` the API serves a few simulated records (`src/db/fallback.ts`) and `meta.source` is `demo`; the app shows `DemoNotice` whenever it sees that.
- **Tests:** PGlite with the real migrations; the importer is tested end to end with a workbook generated in the test (same headers and quirks as the real export).

## Front-end (`atlas-migracoes`)

Same modular structure as `alis-portfolio`:

```
src/
  app/[locale]/       # routes only; each page.tsx is a thin wrapper delegating to a module
  i18n/               # next-intl: routing.ts (localized pathnames), navigation.ts, request.ts
  locales/            # pt.json, en.json, nested UPPER_CASE namespaces; keys must match (locales.test.ts)
  proxy.ts            # Next 16's middleware (renamed), runs next-intl
  modules/<module>/   # <Name>.tsx, styles/index.styles.ts, tests/, components/<Sub>/..., constants/
  shared/components/  # reused across modules but specific to the Atlas (DemoNotice, ComingSoon, AtlasMark)
  lib/                # env.ts, graphql-client.ts, schemas.ts, atlas.ts (queries)
```

- Routes: `/` the home page, `/explorar` (`/en/explore`) Explorar (at `/` until atlas-migracoes#49), `/trajetorias` (`/en/trajectories`) with each artist's record at `/trajetorias/[slug]`, `/camada-historica` (`/en/historical-layer`), `/rede` (`/en/network`, `?artista=<slug>` opens it centered on that artist), `/sobre` (`/en/about`). `[...rest]` sends unknown paths to the localized 404.
- `app/[locale]/layout.tsx` is the root layout: fonts via `next/font` (Cormorant Garamond for headings, Inter for UI), DS stylesheet, then `globals.css`, which points `--atlas-font-*` at the self-hosted fonts and maps the tokens into Tailwind (`bg-background`, `text-muted`, `text-accent`, `border-line`, `font-serif`). It also renders Vercel Web Analytics and Speed Insights (`@vercel/analytics/next`, `@vercel/speed-insights/next`; free on Hobby, cookieless, reporting only on Vercel deployments, turned on in the Vercel project).
- Always import navigation from `@/i18n/navigation`, not `next/link`.
- **Top bar** (`modules/layout/components/TopBar`): brand, Início (the home page) and the six screens, and the language link. From `xl` (1280px) the screens sit inline as tabs; below it (phones, tablets, small laptops, where they no longer fit beside the brand) they fold behind a "Menu" button (`aria-expanded`, `aria-controls`) that drops them as a list over the page, so the full-screen maps keep their size. The menu closes on any navigation, on Escape (focus back to the button) and on a touch outside the header. Below 420px the button shows only its icon and keeps the name "Menu". Light, kept discreet (asked by Alisson, 2026-10-23): the list unrolls and rolls back by its `clip-path`, its rows slide in one after another, and a gold light runs along its lower edge as it opens; the same light runs along the header's edge on each page (an element keyed by the pathname). The `nav-light` utility in `globals.css` gives every screen a faint glow on hover, the current one a halo and a small twinkling four-point star, and, from `xl`, a line of light under the hovered tab. Every motion stops under `prefers-reduced-motion`.
- **Home page** (`modules/home`, atlas-migracoes#49): a slider modelled on the home of Alisson's portfolio (`components/HeroSlider`: four slides with the project's argument from the deck, each leading to its screen; autoplay driven by the progress line's CSS animation, with pause, arrows and dots, no autoplay under `prefers-reduced-motion`, the slide announced only while paused), over `public/home/mapa-noturno.webp` (`-sm` below `md`), a night map in the style of the reference Alisson sent (chosen by him, 2026-10-23): Natural Earth land, borders and populated places (public domain) drawn as city lights in Web Mercator, and gold arcs from the capitals of the origin countries in the deck (slide 1) to São Paulo and Rio de Janeiro. The arcs are an illustration, not trajectories from the base. The map zooms into the part each slide talks about (Europe, the Atlantic, Brazil). Below it, the collection counters (`components/HomeCounters`, an async server component in a `Suspense`, so the page shows at once and only the counters wait for the API), why the Atlas is needed, its impact on research and on the collection, the five screens and the method, then a quiet footer (`shared/components/SiteFooter`, outside `main`, so it is the page's `contentinfo`) with "Desenvolvido por" and Alisson's AH logo in the Atlas colours, linking to his portfolio (requested by Alisson, 2026-10-23; also at the foot of Sobre since 2026-10-29, strings under `FOOTER`). Its texts come from the deck and from Sobre (`ABOUT` strings are reused for the question and the method). The counters strip is `shared/components/CollectionStats`, shared with Explorar.
- **Explorar map** (`modules/explorar`): MapLibre GL 6 through `react-map-gl/maplibre`, loaded client-only with `next/dynamic`. MapLibre 6 looks for its worker next to its own module, so every client-only map imports `shared/map/worker.ts`, which calls `setWorkerUrl(new URL("maplibre-gl/dist/maplibre-gl-worker.mjs", import.meta.url))` and the bundler emits the worker as an asset. The basemap is a minimal style over OpenFreeMap vector tiles (free, no key): land and water only, colored from the `--atlas-*` tokens, with no present-day borders or place names (the borders of each period belong to the Camada Histórica). Trajectories are built in `lib/trajectory.ts` from the documented points only (birth, exhibitions of the works during the artist's lifetime, death), shown with an "inferred" reliability tag; posthumous exhibitions and points without a date or coordinates are counted, never drawn. Each artist's shown points are joined in date order by Turf great-circle arcs (`lib/mapFeatures.ts`); the legs from the birthplace to the first stop whose country is "Brasil" (`migrationLeg`, when both ends are in the shown period) are tagged `migration` and drawn solid gold, the other legs dashed and light, and the birthplace and first place in Brazil are gold points (decided by Alisson, 2026-10-20). With an artist selected, only that artist's lines are drawn and the other places are dimmed. The lines show the sequence of the records, not a documented route, and the screen says so.
- **Map screens** (`shared/components/MapScreen`): Explorar and the Camada Histórica share one layout. On desktop the map fills the screen under the top bar with no page scroll, and the blocks float over it: the presentation (`intro`) at the top of a 336px left column, over the controls panel, which scrolls inside the column (`scrollbar-atlas`); an optional `footer` runs along the bottom (Explorar's collection counters). Only the blocks take pointer events, so the map stays draggable, and maps that fit or center their view leave `SIDE_INSET` for the column. On mobile the blocks stack under the map. New map screens reuse it instead of copying the grid.
- **Shared trajectory pieces**: `lib/trajectory.ts` and `lib/mapFeatures.ts` (pure, tested), `shared/components/TrajectoryMap` (client-only MapLibre map; import it from the folder index, which lazy-loads it) and `shared/components/TrajectoryStops` (the dated stop list with its "inferred" tag). Explorar and the Trajetórias record both use them.
- **Camada Histórica** (`modules/historical`): the borders file is fetched once on the client (`hooks/useStates`, validated with `statesSchema`) and drawn by `components/HistoricalMap` (client-only, like the trajectory map; it adds OpenFreeMap's free glyphs for state names, one label per state at its largest polygon, and keeps the view inside the clipped area). Decade (DS `SegmentedControl`) and year (`SelectField`) choose the day shown, 1 July. `utils/origins` reads each birthplace in the state at the artist's birth (`stateAtDate`, as uncertain as the date) and in the year shown.
- **Rede Relacional** (`modules/network`): one query (`getNetworkData`) brings each artist with their works and each work's exhibitions and publications; `lib/network.ts` (pure, tested) builds the graph in the browser. Node ids are prefixed by kind (`artist:`, `work:`, `exhibition:`, `publication:`, `institution:<normalized name>`, `place:`), and institutions spelled differently (case, accents, spacing) are one node. The overview links every artist to their birthplace and to the institutions (or, with no institution, the places) that showed their works, weighted by exhibitions; centering on an artist shows their works, the works' exhibitions and publications, those venues, birth and death places, and the other artists in the same exhibitions. The period filter keeps exhibitions and publications whose years touch it; undated records appear only with the full period, which spans the dated records of the base. Layout (`lib/networkLayout.ts`, pure and tested, no graph library) gives position a meaning: the overview reads in columns, left to right (birthplaces, artists, institutions, exhibition cities), rows ordered by a few barycenter sweeps to keep crossings few; an artist's network reads in rings, one link further out each (works and life places, exhibitions and publications, venues and other artists), with the nodes that share a venue kept side by side. Layouts are deterministic and rounded to a hundredth, and sort labels without `localeCompare`, so server and browser draw the same picture (no hydration mismatch). The graph is plain SVG with one focusable button per node, sized by its links; birth and death links are dashed. It zooms with the wheel or buttons and pans by dragging (by hand, no library); `visibleLabels` writes only the labels that fit without overlap at the current zoom, cut to the room before the next column, and always writes the selection's links as a stacked list. The page fills the screen on desktop like Explorar, with no page scroll: a left column with the presentation over the panel (which scrolls inside, `scrollbar-atlas`) and the credit, and the graph on the rest; below `lg` they stack, graph before the credit. The panel uses the DS `Legend`, `SelectField` and `YearRange`. Links are tagged "documented", since they come straight from the spreadsheets.
- **IA Relacional** (`modules/research`, route `/ia-relacional`, en `/relational-ai`): the artist is chosen in a `SelectField` and goes in the URL (`?artista=<slug>`, also linked from the record), so the server page asks the API for `research(slug)` and the screen is shareable. The collection's record (birth and death) sits beside the Wikidata person the API matched and why it was chosen (birth year or exact name), the Wikipedia summary, and each statement grouped by property with its `ReliabilityTag`, reference count, source link and review notes (present-day place names, dates that disagree with the collection). The sources consulted, when they were read and how the search works are always shown. With no certain match the screen says so and shows no findings; a Wikidata error is told apart from no match. Source links must be https (validated by Zod). Every finding is numbered by its position in `research.findings` (anchor `#achado-n`), and the AI summary (`research.summary`, written by Gemini in the API) links each `[n]` it cites to that finding; only citations of existing findings become links (`summaryParts` in `lib/research.ts`). When the API withholds the text (no key, rejected or error) the screen says why. The prompt sent to the model is shown in a collapsible block under the method, and the period's map the model is given (`research.period`: the state that held the birthplace on 1 July of the birth year and the states of Europe that day, from CShapes) has its own panel linked to the Camada Histórica. The screen spans the full width with the Trajetórias margins and the picker beside the title; from `lg` the record, the period's map, the sources and the method sit in a left column beside the reading (search overview, Wikidata person, AI summary, encyclopedia summary), and from `xl` the findings take a third column beside the summaries that cite them (the reading takes both columns when there is no match). Small screens stack them in reading order.
- **Shared map pieces** (`shared/map`): `mapStyle.ts` (bare basemap, optional glyphs, token colors), `worker.ts` (MapLibre worker URL, imported by every client-only map) and `preconnect.ts`; `shared/hooks/useIsDesktop`.
- **Map loading.** MapLibre (about 285 KB gzip, plus its 143 KB worker) is only downloaded on the screens with a map, after the page shows, behind a placeholder. While it downloads, the lazy map components preconnect to the tile server (`preconnectTiles`, a `<link rel="preconnect">` already in the server HTML). `useStates` preloads the borders file (`<link rel="preload" as="fetch">`), so its download starts with the HTML instead of after hydration; the fetch reuses it. `next.config.ts` lets browsers and the CDN keep `/cartography/*` for a day (`stale-while-revalidate` a week); the file is about 640 KB, about 50 KB compressed. Measured 2026-10-20 against the simulated API: the screens without a map load about 520 KB of JavaScript before compression.
- **Loading states** (atlas-migracoes#48). Every screen that reads the API has a `loading.tsx` (the route's Suspense boundary) that shows at once a skeleton of that screen while the server waits for the data: the DS `Skeleton` blocks, lines and circles in the screen's own layout (the map screens reuse `MapScreen` through `MapScreenSkeleton`), with the static presentation (eyebrow, title, intro) already written where it does not depend on data. The skeletons are decorative; `shared/components/Loading` wraps them in one `role="status"` region named "Carregando…". On the IA Relacional the findings stream in their own `<Suspense key={slug}>` (`ResearchLoader`), so the page waits only for the artist list, and choosing another artist swaps the findings for their skeleton at once: the picker's navigation runs in a transition shared through `ResearchTransition`, and `PendingResults` shows the skeleton while it is pending instead of leaving the previous artist on screen.
- **Trajetórias record** (`modules/trajectories`): works, exhibitions and publications come straight from the MAC USP spreadsheets and are tagged "documented"; the trajectory is tagged "inferred". Unknown slugs go to the localized 404; a failed request to the error boundary.
- Pages that read collection data use `dynamic = "force-dynamic"` (Axios, not `fetch`, so Next can't infer it) and render a fallback when the API is unreachable instead of failing.

## Test coverage

Test coverage is a premise of the architecture, decided by Alisson on 2026-10-18: the platform is presented live at MAC USP and maintained by one person, so every repo measures its coverage and CI blocks a PR that drops it below the floor.

- **How:** Vitest with the V8 provider (`@vitest/coverage-v8`, free). `yarn test:coverage` prints the report (text, plus `coverage/index.html`); CI runs it instead of `yarn test`. The thresholds live in each repo's Vitest config.
- **Floors** (lines / statements / functions / branches):

  | Repo | Floor | Measured on 2026-10-18 |
  | --- | --- | --- |
  | `atlas-migracoes` | 95 / 95 / 90 / 85, and 95 / 95 / 95 / 90 for `src/lib` | 98.5 / 97.8 / 95.3 / 90.1 |
  | `atlas-migracoes-api` | 95 / 95 / 95 / 90 | 98.6 / 98.6 / 96.5 / 92.7 |
  | `atlas-migracoes-design-system` | 100 / 100 / 100 / 95 | 100 / 100 / 100 / 100 |

  A floor only goes up: when a PR raises coverage, it raises the floor too.
- **What is not measured, and why:** only code with no logic of its own. App: the Next.js route files in `src/app` (each `page.tsx` stays a thin wrapper delegating to a tested module), `src/i18n` and `src/proxy.ts` wiring, and barrels (`index.ts`); these are exercised by `next build`. API: entry points that only wire env, files and exit codes around tested functions (`src/index.ts`, `src/**/cli.ts`, `src/db/migrate.ts`, `api/graphql.ts`) and the declarative Drizzle tables (`src/db/schema.ts`, checked by the PGlite migrations in every test). DS: barrels. Logic never moves into these files to dodge the floor.
- **What the numbers do not prove:** behaviour in a real browser. That is the job of the Playwright suite in `e2e/` (see "Smoke and accessibility tests" below).

## Smoke and accessibility tests

`yarn test:e2e` (Playwright, Chromium, desktop and a Pixel 7 viewport) runs the built app (`yarn build` first) against `e2e/mock-api.mts`, a stand-in for the API that answers each GraphQL operation by name with simulated records (`meta.source = demo`; no collection data in the repo). The mock listens on the API's default local URL, `http://localhost:4000/graphql`, so the default build already points to it. CI runs it in a separate `e2e` job on every PR.

- `e2e/smoke.spec.ts` is the conference demo script: the home page and its slider to Explorar, Explorar to an artist's record, the record to the IA Relacional and a citation to its finding, Camada Histórica, Rede Relacional, Sobre, the language switch keeping the page, and the skip link.
- `e2e/a11y.spec.ts` runs axe (`@axe-core/playwright`) on every screen in PT and EN and fails on any serious or critical WCAG 2.1 A/AA violation it can detect. What axe cannot judge (reading order, keyboard use of the map and the graph) is checked by hand before the deploy.
- `yarn test:launch` (`playwright.launch.config.ts`, `e2e/launch/`) runs the same demo script against a deployed address with the real base: production by default, or `LAUNCH_URL`. It names no artist (it follows the first one each list shows), fails if any page shows the demo-data notice, and builds or starts nothing. CI does not run it; it is the launch check, and a rehearsal before it.
- Every page has a "Pular para o conteúdo" link as the first Tab stop, pointing to `#conteudo` (the wrapper in `modules/layout/Layout.tsx`).

## Security headers

Every page is served with the headers in `src/lib/securityHeaders.ts` (wired in `next.config.ts`): `X-Content-Type-Options: nosniff`, `Content-Security-Policy: frame-ancestors 'none'` with `X-Frame-Options: DENY` (the site is never shown inside another site's frame), `Referrer-Policy: strict-origin-when-cross-origin` and a `Permissions-Policy` that turns off camera, microphone, location and topics. The smoke suite checks them on the built app. The CSP limits framing only; a full policy (scripts, styles, the MapLibre worker, OpenFreeMap, the API, Vercel Analytics) is planned after the conference, starting in Report-Only. HSTS comes from Vercel.

## Visual direction

The dark Atlas screens in the project deck (`ap_MIGRACOES.pptx`, slides 12–21): night-blue surfaces, one gold accent, serif headings, small uppercase sans labels, translucent panels over the map, a reliability tag (documented, inferred, undetermined) next to claims. Single dark theme by design.

Brand (chosen by Alisson, 2026-10-20): the "Rosa Leste-Sul", a compass rose whose only gold stroke is the quarter turn from East to South. The header draws it with `shared/components/AtlasMark` (inline SVG coloured by the `foreground` and `accent` tokens) next to the live wordmark text; `src/app/icon.svg`, `favicon.ico` and `apple-icon.png` use the simplified icon (no ring, thicker strokes) on a night-blue square. The full kit (lockups, light and mono versions) lives outside the repo, in the project's files.

## Planned additions (see roadmap)

- Historical cartography: Europe's state borders from CShapes 2.0 (CC BY-NC-SA 4.0), one static file of polygons with validity dates built by `scripts/build-cartography.mts`; the app picks the polygons in force on a day and places birthplaces in them by point-in-polygon. Each state is shown by its name on that day (`public/cartography/state-names.json`, pt and en, via `periodName` in `lib/stateNames.ts`), never by CShapes' single English name; the API reads the same file for `research.period`. See "Historical cartography" in the roadmap.
- Geocoding: a one-time Nominatim script plus manual review, stored in `places`; never a live lookup.
- Admin: Better Auth with the Drizzle adapter, sessions in Postgres, roles admin and researcher.
- E2E: when the admin area arrives, the login joins the smoke flow.
- IA Relacional: an API service that searches open sources (Wikidata, Wikipedia) and uses the Gemini API free tier to summarise; the key stays in the API's env. Every finding keeps its source URL and a reliability tag, the prompt is returned to the app, and the period's territories go into the prompt so the model reasons only with that period's geopolitics. Findings never enter the base without review.

## Design system consumption

The app installs `@alishenriques/atlas-design-system` from npm (`^0.3.0`; 0.1.0 first published 2026-10-17, 0.2.0 on 2026-10-18 with `SelectField` and `YearRange`, 0.3.0 the same day with `SegmentedControl`, `Legend` and the entity color tokens). New DS versions are released from the DS repo by bumping `version` and pushing a `v*` tag, which runs its publish workflow through npm Trusted Publishing; then bump the range here if the release is a new minor or major. To test unreleased DS changes, temporarily point the dependency at a commit (`github:alishenriques/atlas-migracoes-design-system#commit=…`; Yarn builds it through `prepack`) and never merge that pin.
